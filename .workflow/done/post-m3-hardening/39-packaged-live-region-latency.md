## Findings

**Answer: yes on the fixed packaged tree.** Three consecutive sends in three distinct new sessions exposed a named `role=status` / `aria-live="polite"` / `atomic` node 12, 12 and 10 ms after the run POST response arrived, and all three sessions reached `idle` with the assistant reply `Working chunk 1. Working chunk 2. Working chunk 3.` The same scenario on the unchanged tree measured 543, 648 and 617 ms with the same completion outcomes, so the change is measured against an identical packaged scenario and build path.

**Timing origin.** `t0` is the renderer completion of `POST /api/agent/v1/sessions/:id/runs` (the Host accepted the send; the loopback response arrival follows acceptance by the local transport delta). The end is the first named polite node in `Accessibility.getFullAXTree`. A node can precede the observed response arrival by a few milliseconds because the Host's live status reaches the renderer before the acknowledgement finishes; the strict upper bound from dispatching the run POST is therefore `responseMs + statusMs`: 343, 189 and 210 ms, still inside 400 ms. The interval includes Host-side worker startup only when the Host withheld the 202 for it (reported per run as `requestDurationMs` 331, 177 and 200); provider connection happens after acceptance and is not what gates the measured status. `clickToFirstStatusMs` (6632, 5520, 5309) additionally contains session creation, directory preparation and navigation for a brand-new session, so it is not the checked interval and is reported only to keep the phases distinguishable. DOM insertion was exposed within one animation frame before each AX read (`aria-atomic` observed true), so UI render latency is a few milliseconds, not the former ~500 ms.

**Measured cause (two owners, both changed):**
1. **Rider mount gate.** `ChatContainer` mounted the composer-anchored status region only when `sessionMessages.length > 0`. A brand-new session's accepted run is authoritative control state before any message exists: traced in the packaged renderer, the run acknowledgement moved the session's directory store from `unavailable` to `running` and cleared its invalidation while `messages` was still 0, and the working state lasted ~95-640 ms before the first snapshot message. The live region therefore mounted only when the first message snapshot landed (~500-650 ms after acceptance), never because the status was late. The gate now also mounts on the working state, matching the existing empty-state and hydration-skeleton conditions that already treat a working session as having content.
2. **Resumed event-stream CORS.** The packaged renderer sends `Last-Event-ID` when a session event stream resumes. The Host CORS allowlist did not include that header, so the preflight was refused, the stream could not recover, and the directory's authoritative status was invalidated to `unavailable` (observed as status flapping in the diagnostic trace). The Host allowlist now includes `Last-Event-ID`; the fixed packaged log has zero such preflight refusals.

**Hypothesis checked, not confirmed:** the prior inference that `publishRuntimeRun` skips the store needed by the claim was not the visible cause. The packaged trace shows the acknowledgement applied to the session's authoritative chat-directory store (`statusBefore: "unavailable"` → `statusAfter: "running"`, invalidation cleared). No directory is guessed and `installRuntimeRun`'s no-store early return is untouched; the fix consumes the authoritative status the acknowledgement already publishes.

**Completion and restore.** All three fixed sends reached `idle` with the assistant reply and no `Worker initialization failed` / `SESSION_RESTORE_FAILED` line in either the packaged app log or the Host log (0 occurrences in both baseline and fixed runs). The worker restore path was not modified; the earlier single failure in five Task22 attempts remains unproven and unclaimed.

**Consumer-visible regression.** `ChatContainer.status-live-region.test.tsx` mounts the real chat column under `SyncProvider` with an accepted-run snapshot (`runtimeStatus: "running"`, `activeRunId` set) and zero timeline messages, then asserts a named `role=status` / `aria-live="polite"` node and the Stop control. It passes with the mount change and fails when the old message-only gate is restored.

The fixed AppImage was built from that same base with the change files present in the working tree (its build log records `HEAD=74338fd78` plus the modified `ChatContainer.tsx` and `server/index.js` and the untracked regression test), and those files are the content committed as `a3e0e9c34` on the isolated task branch; the docs-only changes that followed do not affect the bundle. **Limitations.** Linux x64 only; Xvfb without a screen reader, so accessibility-tree exposure is not speech. The provider is a local deterministic fixture, so remote provider connection latency is outside this measurement (it also does not gate the accepted-run path). Only new-session sends were measured; the existing-session path was observed earlier at 282 ms. `/user/emails` 404 retry noise from the remote-provider profile is absent by construction in this fixture. No macOS/Windows or physical-mobile run; the shared UI change applies to Web, Electron, hosted mobile and Capacitor by construction, but only Electron packaged was measured.

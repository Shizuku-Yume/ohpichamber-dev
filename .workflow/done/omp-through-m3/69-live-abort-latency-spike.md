## Findings

**Result:** The abort latency, the 404 and the completed turn are not one defect. With a warm worker and a direct HTTP client (no browser), one 30-second fixture run aborted through the real Host route completed in **559 ms** with `200` and `run.status: "cancelled"` for the same `runId`; the native snapshot then read `runtimeStatus: "idle"`, `activeRun: null` and the turn `cancelled`, stable for 3 s. The 13 s/43 s/no-reply latencies did not reproduce and are not queueing on the control hop: during the in-flight abort, unrelated Host reads returned in 13–65 ms. The **completed turn is a read-time projection defect** in `WorkerProjection.readHistory`, plus two latent settlement races that can latch the same wrong status.

**Why the interrupted turn reads `completed`:** `WorkerProjection.readHistory` sets `status: terminal?.status ?? 'completed'` (`worker/projection.ts:551`) for any turn with no `TURN_TYPE` terminal entry. A live run has only `run.started` + the user message, so a history/bootstrap read of an in-flight turn reports **`completed`** — observed at +102 ms while the abort was still pending, and exactly the shape Task 65 listed 13 s later ("last turn completed for the same runId"). It flips to `cancelled` only once `finish('cancelled')` appends the terminal (`projection.ts:437–456`), which is what the post-abort reads show. It is not an overwrite of a settled run. Two latent races can make the latch permanent:
1. `turn_end` (`projection.ts:408–412`) emits `turn.completed` and `recordTurn('completed')` whenever `stopReason` is still `undefined`; if the aborted assistant `message_end` arrives after `turn_end`, `agent_end` (`projection.ts:414–419`) cancels only the run, while `recordTurn` no-ops (`turn.open` false) — run `cancelled`, turn `completed` (not observed here; the aborted `message_end` preceded `agent_end`).
2. `promptTask` `.then` calls `completeRun` when `session.prompt()` resolves `!dispatched` (`worker/session.ts:537`); an abort that lands before prompt dispatch (`case 'abort'` at `session.ts:544–554`) then calls `cancelRun` after `await session.abort()`/`await promptTask`, so whichever mutates the shared run object first wins. The abort reply `{ ...run }` (`session.ts:554`) is a spread of that mutable object taken after the awaits, so it acknowledges the winner, not the request.

**404 and no-reply:** Not reproduced; they are **late evaluation**, not a stale registry binding. `registry.abort` reads `activeRunId` synchronously from the journal (`registry.ts:709`) and the journal's `settleRun` clears it exactly on `run.cancelled/completed` (`projection/journal.ts:184–194,202–203`); when the request is evaluated after natural completion the registry returns `RUN_NOT_FOUND` by design. Task 65's run `63f9cc88` got 404 at 44.7 s against a 30 s fixture, i.e. after natural completion; the same instance's cold-start costs (58 s session create, 6–19 s run ack) and the browser probes' per-origin connection queue explain 13 s/43 s/>60 s. In this warm, browser-free trace the identical hop took 559 ms and the live check passed 799 ms after run start.

**Smallest fix Task 70 must make:**
1. `packages/agent-service/src/worker/projection.ts`: add a per-run `requestCancel(runId)` latch; while it matches, `consume('agent_end')`, `turn_end` and `finish('completed')` settle `cancelled` and never `completed`; clear it in `beginRun`. Change the `readHistory` fallback at line 551 from `'completed'` to the live status (`'running'`, or the active run's status) so an in-flight turn is never projected as finished.
2. `packages/agent-service/src/worker/session.ts:544–554`: set the latch before `await this.session.abort()`, gate the `!dispatched` `completeRun` branch at line 537 on the latch, and return the settled run rather than a spread of a mutable object (line 554).
3. Leave `registry.ts:709` `RUN_NOT_FOUND`, `routes.js:365` abort-only/scope checks and Host `scopeFor`/`assertWritable` unchanged.

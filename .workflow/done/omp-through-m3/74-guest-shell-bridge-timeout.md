**Root cause and owner.** The Guest receives `HostRequestError: Host did not answer in time.` from `packages/sdk/src/host.ts` `send()` after `GUEST_REQUEST_TIMEOUT_MS` (20 s). It is the SDK's bridge timer, so it says nothing about the HTTP status: a canonical rejection would have arrived milliseconds later as a typed `HostRequestError` (`NOT_FOUND`, `SERVICE_UNAVAILABLE`, or the `CanonicalApiError` fallback in `answerGuestMessage`). It is not a route mismatch: the compiled UI calls the same `canonicalClient.getShellOutput` / `stopShell` routes, with `encodeURIComponent(jobId)`, that a direct authenticated `GET /api/agent/v1/sessions/:id/shell/jobs/:jobId/output?epoch=…&workerGeneration=…&cursor=0&tailBytes=2048` answered in 2205 ms. It is not a long-poll: the Host route forwards one request, and `ShellCoordinator.handle` → `WorkerShell.output` are synchronous; there is no wait/stream flag in `ShellOutputRequestSchema`.

The missing answer is owned by the Host-side bridge, not by the Guest projection: `packages/ui/src/components/layout/PluginPane.tsx` `shellOutput` → `packages/ui/src/lib/guests/shells.ts` `readGuestShellOutput` → `canonicalClient.getShellOutput`, and `PluginPane` `shellStop` → `canonicalClient.stopShell`. That path has no deadline and no `AbortSignal`; the 20 s Guest timer is its only bound. The stop evidence settles the remaining question: the target job stayed running until the Host shut down, so the stop did not take effect. A reply that was merely posted too late or dropped after a successful call would still have killed the job. The canonical call therefore did not complete, and the bridge is the last owner that can answer the Guest.

**Blocking layer (chosen fix boundary).** Two Host-side conditions can consume the bridge budget before the answer: the Guest bridge gated the reply on frame ownership that can change during the canonical round trip, and every session-scoped canonical route - including shell observation - re-ran `admitWorkspace` (`getEnvironmentForDirectory` plus `POST /internal/workspaces/:id`) inside the canonical proxy. That admission shares the Agent Service catalog queue and is unnecessary for observing an already-running worker's shell. The queue routes already avoid it by using `resolveHostSessionScope` instead of `resolveSessionScope`; shell observation takes the same authorized, admission-free path. The bridge additionally gets a deadline, cancellation and a guaranteed typed answer, so a future stall is reported truthfully instead of expiring silently.

**Chosen shape.** Add `packages/ui/src/lib/guests/shell-requests.ts`: one owner that looks up the tracked shell, performs the canonical read/stop with an `AbortController`, enforces a 15 s deadline, maps abort to `HOST_TIMEOUT`, and exposes `abortAll()`. `PluginPane` holds one instance per pane effect, aborts it in cleanup and on runtime switch, and posts the completion on the captured `MessagePort` while it is still current and the runtime key is unchanged. `readGuestShellOutput` and `canonicalClient` accept the optional signal; identity validation stays where it is. In `canonical-routes.js`, mark the shell observation routes (`GET shell/jobs`, `GET …/output`, `POST …/stop`) with an admission-free session resolver wired from `agent-runtime.js`'s existing `resolveHostSessionScope`; leave `POST …/shell/jobs` and all other routes unchanged. No new wire type, route, permission or long-poll is added.

**Rejected alternatives.** Raising the Guest deadline (or using the 90 s `generate` deadline) only moves the cliff and would not have stopped the job, which shows the request itself did not complete. Adding a server-side shell-output long-poll changes the canonical contract and hides the Host blockage. Letting the Guest call the canonical route directly, adding a Host loopback shortcut, or relaxing the `shells` grant bypasses the Guest boundary. Caching shell output in the UI store would duplicate authoritative output, add eviction/retention rules, and still leave stop unanswered.

# Sécurité

OhPiChamber donne accès à votre machine et à votre code ; verrouillez-le donc avant que quelqu’un d’autre que vous puisse l’atteindre. Cette page couvre le mot de passe UI, les passkeys et ce qu’il faut savoir avant d’exposer OhPiChamber sur un réseau.

## Définir un mot de passe UI

Démarrez OhPiChamber avec un mot de passe et l’UI navigateur le demandera :

```bash
ohpichamber --ui-password be-creative-here
```

Vous pouvez aussi le définir avec la variable d’environnement `OPENCHAMBER_UI_PASSWORD` au lieu de le mettre en ligne de commande. Après connexion, OhPiChamber mémorise l’appareil pendant un moment pour ne pas vous le redemander à chaque fois.

Définissez toujours un mot de passe si l’instance est joignable par quelqu’un d’autre — surtout via un [tunnel](/fr/tunnels/) ou internet public.

## Passkeys

Une fois un mot de passe défini, vous pouvez ajouter des passkeys (Face ID, Touch ID, clé de sécurité) pour vous connecter plus vite. Ajoutez-les dans **Paramètres → OhPiChamber → Passkeys**.

Les passkeys sont liées au mot de passe actuel. Si vous changez ou supprimez le mot de passe, les passkeys enregistrées sont effacées et vous devrez les ajouter à nouveau.

## Tokens d’appareil

Les appareils associés via [Connecter un appareil](/fr/connect-devices/) s’authentifient avec leurs propres tokens par appareil, pas avec le mot de passe UI. Les liens d’association sont à usage unique et expirent s’ils ne sont pas utilisés ; chaque appareil associé est listé dans **Paramètres → Instances distantes → Se connecter à ce serveur**, où vous pouvez révoquer n’importe lequel à tout moment. Les connexions hors du domicile passent par le [Relais privé](/fr/private-relay/), qui est chiffré de bout en bout et ne peut pas lire votre trafic.

## Avant de l’exposer

- Par défaut, OhPiChamber n’écoute que sur votre propre machine (`127.0.0.1`). Écouter plus largement demande un changement volontaire, et vous devriez définir un mot de passe d’abord.
- Pour vos propres appareils, préférez l’[association](/fr/connect-devices/) avec le [Relais privé](/fr/private-relay/) — rien n’est exposé publiquement du tout.
- S’il vous faut une URL publique, préférez un [tunnel](/fr/tunnels/) ou un réseau privé (comme un VPN) plutôt que d’ouvrir un port sur internet.
- Si vous placez OhPiChamber derrière votre propre serveur HTTPS, consultez [Reverse proxy](/fr/reverse-proxy/).

## Mode entreprise

Si votre équipe ne peut envoyer le contenu des conversations qu’aux fournisseurs de modèles configurés dans le Host, activez le mode entreprise. Il y a deux façons de le faire, et une seule suffit.

### Un fichier de politique sur la machine

C’est la méthode à utiliser sur les portables que vous gérez. Placez un fichier nommé `policy.json` dans un dossier où seul un administrateur peut écrire :

| Système | Chemin |
|---|---|
| macOS | `/Library/Application Support/OhPiChamber/policy.json` |
| Windows | `C:\ProgramData\OhPiChamber\policy.json` |
| Linux | `/etc/openchamber/policy.json` |

Le chemin ne dépend pas de la façon dont OhPiChamber est installé. L’application de bureau, le serveur web lancé depuis npm et la CLI lisent tous le même fichier. Vous pouvez le déployer avec votre outil de gestion des appareils (Jamf, Intune et autres). Pour un serveur dans Docker, montez le fichier au chemin Linux.

```json
{
  "enterpriseMode": true,
  "organization": "Acme",
  "relayUrl": "wss://relay.acme.com/ws",
  "allowNetworkAccess": false,
  "allowedExtensions": ["https://github.com/acme/"],
  "jev": {
    "url": "https://llm.acme.com/v1/systemone",
    "model": "acme-classifier",
    "apiKey": "..."
  }
}
```

Seul `enterpriseMode` est nécessaire. `organization` s’affiche dans les Paramètres sous la forme « Géré par Acme », pour que chacun sache qui a pris la décision. `relayUrl` et `jev` fixent votre propre relais et votre propre point de terminaison Jev, `allowNetworkAccess` permet à d’autres appareils d’atteindre OhPiChamber par le réseau, et `allowedExtensions` liste les dépôts d’extensions auxquels vous faites confiance. Tous sont décrits plus bas.

- Rien de ce qu’un utilisateur règle, dans les Paramètres ou dans l’environnement, ne désactive ce que le fichier active.
- Quand le fichier active le mode entreprise, seul le fichier décide. Les variables d’environnement ci-dessous pour le relais, Jev et l’accès réseau sont ignorées, car un utilisateur peut les définir lui-même.
- Si le fichier existe mais ne peut pas être lu ou n’est pas un JSON valide, le mode entreprise reste actif et rien n’est fixé. Les Paramètres indiquent que la politique n’a pas pu être lue. Un fichier cassé ne lève jamais la protection en silence.
- Les modifications s’appliquent sans redémarrage.
- OhPiChamber tourne sous le compte de l’utilisateur, donc l’utilisateur peut lire le fichier. Pensez-y avant d’y mettre une clé d’API.

### Une variable d’environnement

Sur un serveur ou dans un conteneur, où vous maîtrisez l’environnement, ceci suffit :

```bash
OPENCHAMBER_ENTERPRISE_MODE=1
```

Sur un portable, c’est un verrou plus faible : l’application de bureau la lit dans le profil du shell de connexion (par exemple `~/.zshrc`), et l’utilisateur peut le modifier. Utilisez plutôt le fichier de politique.

Avec la variable, le relais, Jev, l’accès réseau et les extensions autorisées viennent eux aussi de leurs propres variables : `OPENCHAMBER_RELAY_URL`, `OPENCHAMBER_JEV_URL`, `OPENCHAMBER_ALLOW_NETWORK_ACCESS=1`, `OPENCHAMBER_ALLOWED_EXTENSIONS` (des URL de dépôts séparées par des virgules) et `OPENCHAMBER_ALLOW_LOCAL_EXTENSIONS=1`. Dans Docker, il vous faudra celle de l’accès réseau, puisque le serveur doit écouter au-delà du conteneur.

### Masquer les catalogues de skills intégrés

OhPiChamber est livré avec quelques catalogues de skills publics (Anthropic, OpenAI, Cursor, Matt Pocock). Si votre organisation tient le sien, ajoutez-le comme catalogue personnalisé et masquez les catalogues intégrés dans le fichier de politique. Cela fonctionne avec ou sans le mode entreprise.

```json
{
  "hideBuiltinSkillCatalogs": true
}
```

Les réglages ne proposent alors que les catalogues ajoutés par les utilisateurs, et OhPiChamber ne charge aucun catalogue intégré, même sur demande directe. Il n’y a pas de variable d’environnement pour cela, car un utilisateur peut les définir lui-même.

### Exemples

Pour placer le fichier de politique sur un Mac, exécutez ceci dans le Terminal en tant qu’administrateur :

```bash
sudo mkdir -p "/Library/Application Support/OhPiChamber"
sudo tee "/Library/Application Support/OhPiChamber/policy.json" > /dev/null <<'JSON'
{
  "enterpriseMode": true,
  "organization": "Acme"
}
JSON
```

Sous Linux, c’est pareil avec `/etc/openchamber` comme dossier.

Sous Windows, lancez PowerShell en tant qu’administrateur. La dernière ligne ne laisse le dossier accessible en écriture qu’aux administrateurs et au système :

```powershell
New-Item -ItemType Directory -Force "C:\ProgramData\OhPiChamber" | Out-Null
@'
{
  "enterpriseMode": true,
  "organization": "Acme"
}
'@ | Set-Content -Encoding UTF8 "C:\ProgramData\OhPiChamber\policy.json"
icacls "C:\ProgramData\OhPiChamber" /inheritance:r /grant:r "Administrators:(OI)(CI)F" "SYSTEM:(OI)(CI)F" "Users:(OI)(CI)RX"
```

Un serveur dans Docker, ajouté à l’`environment` de `docker-compose.yml`. Le conteneur écoute au-delà de lui-même, il lui faut donc l’accès réseau autorisé :

```yaml
environment:
  OPENCHAMBER_UI_PASSWORD: ${OPENCHAMBER_UI_PASSWORD}
  OPENCHAMBER_ENTERPRISE_MODE: "1"
  OPENCHAMBER_ALLOW_NETWORK_ACCESS: "1"
  # Optional:
  OPENCHAMBER_RELAY_URL: wss://relay.acme.com/ws
  OPENCHAMBER_JEV_URL: https://llm.acme.com/v1/systemone
  OPENCHAMBER_JEV_MODEL: acme-classifier
  OPENCHAMBER_JEV_API_KEY: ${ACME_JEV_KEY}
  OPENCHAMBER_ALLOWED_EXTENSIONS: https://github.com/acme/
```

Pour vérifier que ça a marché, ouvrez Paramètres → Fournisseurs : un avis sur le mode entreprise avec le nom de votre organisation apparaît en haut.

### Ce qui change

- La gestion des fournisseurs de modèles et des identifiants est assurée par le Host. En mode entreprise, les opérations d’ajout de fournisseurs — connecter un fournisseur, ajouter ou configurer des fournisseurs ou modèles personnalisés, écrire des identifiants, découvrir des modèles ou initier un flux OAuth — sont refusées par le Host ; supprimer ou changer de compte existant fonctionne toujours. Les serveurs MCP configurés pour la session ou l'espace de travail continuent de fonctionner, car ils se connectent à ce serveur et non à un fournisseur de modèles. Le preflight explicite de transmission d’identifiants est également refusé par le Host lorsque le mode entreprise est activé ; aucun identifiant n’est lu ni importé.
- Le remplissage des informations de modèle n’atteint jamais OpenRouter en mode entreprise. La requête n’envoie de toute façon que des identifiants de modèle ; le mode activé la refuse, donc le remplissage automatique répond à partir du catalogue fourni avec l’application, et les modèles que ce catalogue ne connaît pas gardent leurs champs vides.
- La connexion à un serveur MCP reste désactivée. Le Host refuse le démarrage d’une connexion MCP et le rappel du navigateur qui l’achève (`403 enterprise_mode`). Les serveurs sans connexion, y compris les serveurs locaux qui prennent des valeurs d’environnement, ne sont pas concernés.
- Le Host bloque les recherches web natives au moment de la sortie réseau et empêche l’ajout ou le remplacement d’identifiants de recherche. Vous pouvez toujours modifier les paramètres de recherche ou supprimer les identifiants enregistrés ; les clés sont en écriture seule et ne sont jamais renvoyées.
- Les [Fournisseurs de classification (Jev)](/classification-providers/) restent désactivés, y compris un point de terminaison personnalisé que quelqu’un saisit dans les Paramètres. Le filet de sécurité et Auto ne sont pas proposés, et les sessions ne passent en cours qu’à la main. Pour utiliser Jev via votre propre infrastructure, fixez un point de terminaison avec `jev` dans le fichier de politique, ou avec `OPENCHAMBER_JEV_URL` (plus `OPENCHAMBER_JEV_MODEL` et, s’il en faut une, `OPENCHAMBER_JEV_API_KEY`). Il devient le choix par défaut, on peut toujours le désactiver, et rien d’autre ne peut être choisi.
- La lecture à voix haute via OpenAI est désactivée. Un serveur personnalisé de synthèse vocale ou de transcription doit tourner sur la même machine. Les voix locales et les modèles de dictée locaux continuent de fonctionner.
- Les notifications push vers les téléphones et les navigateurs ne portent qu’un titre générique comme « Agent response is ready », sans texte de message ni nom de session. Les notifications de bureau restent sur votre machine et gardent le texte complet.
- Les [tunnels externes](/fr/tunnels/) (Cloudflare, ngrok, Tailscale) sont désactivés. Cloudflare et ngrok déchiffrent le trafic à leur périphérie et voient chaque requête en clair ; Tailscale Serve et Funnel ouvrent cette machine à d’autres appareils.
- Les diagrammes `.drawio` s’ouvrent sous forme de texte XML. L’éditeur de diagrammes est une page de diagrams.net, et y ouvrir un diagramme lui transmet le fichier.
- Le catalogue d’intégrations de la barre latérale est masqué. Il installe des services externes depuis une liste fournie avec OhPiChamber. Ajouter des serveurs MCP, des plugins et des skills dans les réglages fonctionne comme avant.
- Les polices d’interface et de code chargées depuis un CDN public reviennent aux polices du système. Votre choix est conservé pour le jour où le mode est désactivé.
- Le [Relais privé](/fr/private-relay/) ne fonctionne qu’avec un relais auto-hébergé configuré via `relayUrl` dans le fichier de politique ou `OPENCHAMBER_RELAY_URL=wss://relay.example.com/ws`. OhPiChamber n’inclut aucun relais partagé intégré (et les notifications push iOS distantes nécessitent `OPENCHAMBER_PUSH_RELAY_URL` ou une configuration APNs directe) : votre propre relais garde ainsi les métadonnées de connexion et l’accès à cette machine à l’intérieur de votre réseau. Sans URL de relais configurée, aucun appareil ne peut être associé via le relais.
- Les pages que l’agent partage avec d’autres personnes par lien et code PIN passent uniquement par votre propre relais, celui défini avec `relayUrl` ou `OPENCHAMBER_RELAY_URL`. Le relais ne garde que la page et la réponse chiffrées, mais le lien y mène. Sans votre propre relais, le partage n’existe pas : l’agent ne se le voit pas proposer et le serveur le refuse. Ouvrir une page qu’une autre personne a partagée fonctionne de la même façon : OhPiChamber n’ouvre que les liens de votre propre relais, et sans lui un lien collé reste du texte.
- OhPiChamber n’écoute que sur la machine où il tourne. Le réglage de bureau qui permet aux autres appareils du réseau local d’ouvrir l’application est désactivé, et le serveur refuse de démarrer sur une adresse réseau, que ce soit via la CLI (`--host`, `--lan`) ou via l’environnement. Si le fichier de politique apparaît pendant que l’application tourne, les connexions depuis d’autres machines sont coupées jusqu’au prochain démarrage. Autorisez l’accès réseau avec `"allowNetworkAccess": true` dans le fichier de politique, ou avec `OPENCHAMBER_ALLOW_NETWORK_ACCESS=1` là où l’environnement active le mode entreprise. Gardez en tête que la connexion passe en HTTP simple, donc sur un réseau partagé n’importe qui peut la lire ; placez un serveur que d’autres atteignent derrière [votre propre HTTPS](/fr/reverse-proxy/).
- Les [extensions](/fr/extensions/) qui peuvent envoyer des données hors de la machine (celles qui parlent à une API externe, chargent depuis des adresses externes, font tourner un service en arrière-plan, font envoyer à ce service ce que l’agent dit dans les sessions, lisent les sessions du Host ou démarrent des sessions, répondent aux demandes d’autorisation de l’agent, ajoutent des instructions, fournissent des skills aux agents) ne s’installent que depuis un dépôt Git listé dans `allowedExtensions`. Une extension autorisée qui transmet des notifications ne reçoit que le titre générique, sans texte de message, nom de session ni projet, comme le téléphone. Une extension autorisée qui sert d’outil de suivi reçoit vos recherches et les identifiants des éléments que vous ouvrez, et les commentaires de session qu’elle publie portent un libellé fixe et un lien vers la session, jamais ce qui s’y est dit. Une extension autorisée qui rapporte la consommation reçoit les identifiants que le Host conserve pour les fournisseurs listés dans son manifeste, que vous avez approuvés dans son dialogue, et rien de vos sessions. Les extensions qui ne font rien de tout cela s’installent comme d’habitude. Une extension installée depuis n’importe où ailleurs reste désactivée, et les Paramètres expliquent pourquoi. La liste contient des URL de dépôts, puisqu’une extension choisit elle-même son nom ; une entrée qui se termine par `/`, comme `https://github.com/acme/`, autorise tous les dépôts en dessous. Sur les machines des personnes qui développent des extensions, `"allowLocalExtensions": true` autorise aussi l’installation depuis un dossier local. Un ZIP reste bloqué dans tous les cas.
- Les variables d’environnement de **Paramètres → Général** n’atteignent pas OMP, car l’une d’elles pourrait contenir une clé de fournisseur. Git, le terminal et les actions de projet les reçoivent toujours.

Les tâches du petit modèle (titres de session, récapitulatifs, messages de commit, la revue guidée des modifications) n’ont besoin d’aucun mode particulier. Elles tournent toujours sur le petit modèle choisi dans les Paramètres, sur un petit modèle du fournisseur avec lequel vous travaillez, ou sur le modèle par défaut configuré dans le Host. Elles ne se rabattent jamais sur un autre fournisseur qui se trouve simplement connecté.

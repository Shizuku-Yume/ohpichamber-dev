# MCP backend integration

## Native Host usage tool

`openchamber_usage` exposes only `usage.read`. It is disabled by default, follows
`agentUsageToolEnabled` on initial worker setup and settings updates, and is
checked again at the Host dispatch boundary. Results use the existing versioned
usage card envelope, without account labels or credentials. `openchamber` also
admits `session.track` and `session.markDone`; Canonical session eligibility,
Host metadata and archive/worktree pin owners enforce their work-state policy.

## Projection validation

Unstamped session update/status projections reuse Canonical payload schemas,
including revision and live-run refinements. Journal stamping adds the actual
envelope and validates the complete event. Projection seeds reuse snapshot state
fields, not snapshot-only cursor/window checks. Refined schemas are never merged
then omitted/picked, which Zod 4.6.7 rejects.

The Agent Service owns workspace MCP configuration and routes sessionless workspace MCP operations through stateless workers. Workspace configuration is persisted by the catalog coordinator; worker operations remain authorized against the workspace root session.

A session worker applies its initial external MCP configuration off the admission path: `WorkerSession.open` starts the application in the background instead of waiting for the handshake, so a slow or unreachable external server cannot delay the first prompt. Connection failures are reported as `mcp.runtime.failure` diagnostics and never fail the worker; a successful application publishes the ready catalog and its tools through `catalog.updated`. `close()` disconnects the MCP owner before awaiting that background application, so a stalled handshake settles rather than holding the worker's shutdown window.

User-scope servers live in OMP's native `~/.omp/agent/mcp.json`. The write is a locked read-modify-write of that file: only entries whose projection changes are rewritten, and native `env`, `headers`, `auth`, `oauth`, `enabledServers` and any global server shadowed by a project server are kept byte-for-byte. A project save never touches the user file. The user file's credential references (`credentialRef`, `headerCredentialRefs`, `envCredentialRefs`) are kept under one top-level `openchamber` key that OMP ignores; secret values are never written there.

With no live session worker, a configure or apply classifies the saved servers by the stateless `test` probe of each enabled server (`saved-needs-auth` when the probe reports an authorization challenge, `saved-not-connected` for any other failure, `applied` only when every probe connects). One classifier, `mcpAuthRequired` in `src/mcp-auth.ts`, decides that for both apply paths: it accepts `MCP_AUTH_REQUIRED`, `AUTH_REQUIRED` and `MCP_CREDENTIAL_UNAVAILABLE`, and reads 401/403/`insufficient_scope`/unauthorized/sign-in/auth out of the code and detail, so which path runs (whether a session happens to be open) cannot change an unauthenticated install into a reported failure. `CatalogCoordinatorOptions.probeMcp` supplies that probe; reconnect uses the same option. That probe's own failure detail is what the refused configure reports: with no worker error to quote, the thrown `MCP_APPLY_FAILED` detail is the probe's cause (the child's own error text, exactly as a worker error detail would be), never the Host sentence about missing workers. A configure that reports `saved-needs-auth` still succeeds with a sign-in action. Every MCP failure detail is scrubbed at its origin (`WorkerMcp.#stage`) against the credential values that transport was given, so a provider that echoes a DSN or token in its own startup error cannot carry it into the catalog, the problem body or a toast. The workspace tools catalog (`GET /api/agent/v1/workspaces/:workspaceId/tools`) reports the MCP tools of the workspace's saved configuration: `CatalogCoordinator.workspaceMcpTools` runs the stateless `discover` operation, which stages a real isolated handshake per enabled server through `CatalogCoordinatorOptions.discoverMcpTools`, names each tool, releases the transports and publishes nothing. The answer therefore exists before any session worker exists. A server that cannot connect contributes no tools; the saved revision still answers. The newest ready session snapshot (by runtime readiness, applied and catalog revisions, worker generation, then root session id) may add tools discovery did not report, and never replaces a discovered tool.

MCP sign-in is a state of the saved configuration, not an install error. The coordinator always sets `MCPApplyResult.outcome` (`applied`, `saved-needs-auth`, `saved-not-connected`); a `saved-needs-auth` result is returned to the caller, while only a genuinely non-auth failure throws `MCP_APPLY_FAILED`. The worker's `isAuthError` accepts the same 401/403/`insufficient_scope` signals. `WorkerMcp` discovers endpoints through OMP's `resolveMcpOAuthEndpointsFromServer`, which probes the server anonymously and reads `WWW-Authenticate`/`Mcp-Auth-Server`; an `issuerUrl` or `resourceMetadataUrl` from the request still wins. A failed sign-in keeps the provider's own sentence: `#toOAuthError` passes a non-native `Error` through and maps a rejected dynamic client registration to `MCP_OAUTH_CLIENT_REGISTRATION_REJECTED` instead of an opaque line. Starting a second flow while one is pending throws `MCP_OAUTH_IN_PROGRESS` (HTTP 409), and cancelling keeps `MCP_OAUTH_CANCELLED`. A flow that fails after the browser handoff (consent denied, state mismatch, token exchange, expiry) has no request left to throw from, so `oauthRead` reports its cause once on the next `unauthenticated` result as `error: {code, detail, retryable}` and retires the entry; a user cancel stays neutral with no error.

## Provider and model catalogs

`GET /api/agent/v1/workspaces/:workspaceId/providers` publishes the complete native provider directory used by Settings: bundled providers, configured `models.yml` providers, stored credentials and OAuth providers. It stays complete so the connection directory can offer a provider that is not configured yet.

`GET /api/agent/v1/workspaces/:workspaceId/models` publishes only executable models. The worker asks the native `ModelRegistry` for its available pool (`getAvailable('all')`), which includes configured providers (including keyless `auth: none` local endpoints), stored and OAuth credentials, environment credentials explicitly present in the Host-authorized directory overlay, and native keyless local providers, and excludes providers whose authentication is missing. Ambient Host environment credentials are not inherited by workers, so an environment-only provider is executable only when its values are configured in that overlay. Model pickers therefore cannot list every bundled provider; the full registry is never the executable catalog. An unreadable or malformed native configuration remains a `503 SERVICE_UNAVAILABLE` read failure, not an empty catalog.

## OMP behaviour settings

`GET`/`PUT`/`PATCH /api/agent/v1/workspaces/:workspaceId/settings` expose the OMP behaviour settings a GUI owner draws or writes. `/workspaces/:workspaceId/omp/settings` is the same operation: both paths address one workspace revision, and `PATCH` is equivalent to `PUT`. The canonical contract is `agent-contract/src/settings.ts`. The setting list is `OMP_SETTING_PLACEMENTS` in `settings-ui.ts`, a placement table over `orderedSettings()`; `OMP_SETTING_EXPOSED_IDS` is the set the route returns and accepts (`engine`, `owned-by`, and page placements a GUI control writes). Each conditional row also carries OMP's `ui.condition` evaluated against the same settings handle: `advisorEnabled`, `composerPredictionsEnabled`, `usageAwareFallbackEnabled`, `planModeEnabled`, `planAutosaveEnabled` and `autoThinkingActive` (which follows `defaultThinkingLevel === 'auto'`, exactly as OMP's terminal panel defines it) report their live state as `conditionActive`, and a condition name this package has not mapped leaves the row active. Descriptor types, defaults, enum values, labels and groups come from the pinned package's `orderedSettings()` metadata, never from a copied schema. PUT changes are parsed against each setting's own `Setting.assertWritable` before any layer changes, so a newer native setting shape is enforced by OMP rather than a loose generic value.

Reads call `Settings.reloadFromDisk()` before projecting values, so an edit made in the OMP TUI appears without restarting the app. Writes call `Setting.set`/`Setting.unset`, await `Settings.flush()` before returning, and reload the file afterwards. The workspace catalog owner supplies uint64 revision CAS: a stale `expectedRevision` returns HTTP 409 `CATALOG_CONFLICT` and a successful write returns the next revision. The stateless worker owns the write, so a live session is not restarted; a new session reads the flushed `config.yml`.

Unexposed settings are omitted from state and refused on write with 400 `INVALID_REQUEST`. That covers credentials (`isCredential`, refused with 422), `tui-only` keys (terminal renderer switches such as `read.renderMarkdown`, `read.toolResultPreview`, `mcp.renderMarkdownResults`, `extensionRenderers.assistantText` and the print-mode `async.printWake`) and untabbed (`hidden`) keys, complex engine settings (`Record`/`Array` without choices) that lack a GUI control, and every `boundary` placement: raw MCP server `command`/`env`/`headers`, `auth.broker.*`, `task.agentAccountPools`, `compaction.remoteEndpoint`, `skills.registryUrl`, the `dev.autoqa` and `spotlight.experiment.enabled` toggles that ship data to `qa.omp.sh` and `cloud.stencil.so` with no GUI consent surface, and other off-host endpoints, keys, relays, listeners and telemetry, and configurable paths (`plan.autosaveDir`, `workspace.additionalDirectories`, `ovnfs.path`, `worktree.base`, `ida.installDir`, `browser.screenshotDir`, `mnemopi.dbPath`, `python.interpreter`). Those remain on their owning provider, MCP, skill or OMP TUI surfaces, or in `config.yml`. `totalCount` counts every OMP setting, so the page's kept-out number is `totalCount` minus the rows it draws. Values are JSON scalars, arrays or records only; public responses never include secret or environment contents. The route is authorized by the existing canonical Host gateway and workspace scope before forwarding, and is not a provider-entry or plugin-egress operation. Web/PWA, Electron, hosted mobile and Capacitor all use the same authenticated route.

## OMP TUI visual parity and tool streaming

OMP 19's SDK emits `agent_end` once per run. `agent_pause` ends an intermediate model loop, not the run: the canonical run and its running status remain open across retries, queued prompts and background-work wakes. Admission checks use `AgentSession.isRunActive`; prompt completion waits for `waitForRunEnd()` before binding final history. End-of-run mode transitions, goal verification and suggestions run only at `agent_end`. Todo projection reconciles native state on start, pause and end as well as tool and turn events. OMP's live `wakeSources` owns whether outside work can resume the paused run; persisted messages never establish live activity.

Historical todo snapshots and reminder notices normalize removed `blocked` statuses to `pending`, while the canonical contract accepts only the four current statuses. Tool transcript details use the same normalization in the UI. Internal spilled-output links use `local://N.log`; they remain SDK-owned URIs, not Host filesystem or external-browser links. `artifact://` is not an allowed internal read scheme.

The removed seance command and IDA tool are not dispatched. `/commit` is deliberately excluded from generic headless slash dispatch: its selective Git mutation bypasses the Host Git capability. Plugin extension discovery uses enabled plugin records and their resolved extension paths. Named services project OMP daemon `proc` units using their key, PIDs and hold policy, retaining the session-owner checks.

OMP 19 journals `/btw` usage on the main branch. Promotion permits only `model_usage` descendants of the question's captured leaf, then passes the current native leaf into `branchFromBtw` for its own transition CAS. A changed conversational or custom entry, missing ancestor or active run still refuses promotion.

Top-level worker sessions are initialized with `tuiTranscript: true`, which informs the pinned OMP SDK that the transcript renders Mermaid, SVG figures, and table auto-charts, and activates `out://` mid-turn replies by default via `outRepliesActive(settings, tuiTranscript)` while respecting user `out.enabled` configuration overrides.

`WorkerProjection` handles `toolcall_start`, `toolcall_delta`, and `tool_stream_update` events to project progressive tool arguments (`write.content`, `edit.input`, `eval.code`) live into `part.started` and `part.updated` canonical events, keeping `status: 'running'` and redacting private paths via `publicJsonObject(...)` before arguments are emitted over the canonical event stream.

## Tool result placement, partial output and step timing

An unrecovered OMP assistant `stopReason: error` retains its `errorMessage` through canonical `run.failed.error`, the journal's failed turn and native canonical terminal entries. The existing shared chat error notice displays that string. The native registry remembers credentials and custom header values resolved for provider calls and removes echoed values, authorization headers and credential assignments before failure detail is projected or persisted as canonical metadata; model selection registers merged native and catalog headers before sending them. Private filesystem roots remain redacted. Empty provider detail keeps the generic failure text. A successful retry clears the earlier failure, and abort intent still takes precedence.

A tool result belongs to the message that authored its `tool_call`: the projection records the call's owner when the call is authored, and publishes the outcome as a `tool_result` part at `<call-part>:result` on that message. OMP's `tool_execution_update` frames become `part.updated` on the same part while the call runs, so a long `bash`/`task` shows its body live; the terminal `tool_execution_end` and the native `toolResult` message both close it. A native result message never becomes a canonical message, and no `system` role is authored for a result. A failed result carries the tool's own detail in `error` and a class in `errorKind` (`synthetic` for a call OMP never ran, `interrupted`, an edit's own `errorKind`, `timeout` from `details.timedOut`, `background-job` from a dead `details.async`, else `tool_error`).

`metadata()` also derives each assistant step's `timing` from the native `AssistantMessage` alone (`timestamp`, `ttft`, `duration`/`completedAt`), so a restored step and the live stream publish the same absolute epochs. A run OMP prompts itself (plan/goal continuation) opens a turn with no authored user message; the Host prompt path authors the user message it was given.

Host tools (`openchamber`, `openchamber_knowledge`, `web`, `memory`, `notify`, `openchamber_image`, `openchamber_render`) are registered by `worker/host-tool.ts`; `openchamber_render` sends the tool call id so a waiting page can be answered, and returns its answer under `details.openchamber`, which the projection also hoists to the result's top level for the render card.

`openchamber_secret` is a Host-owned tool with call identity. `secret.run`
requests Canonical Bash approval for its executable and arguments, then
consumes the one-shot receipt through the existing Host Bash authorizer before
calling the private Host action channel. The Host alone collects values; no
submitted secret enters the worker, SDK transcript or canonical tool result.
`secret.request` refuses file mode and `secret.forget` clears Host memory leases.
The shared private-protocol `hostActionTimeoutMs` policy exempts only `secret.run`
from the generic two-minute IPC deadline in both supervisor and Node Host.
Secret entry waits for the user or cancellation; the Host command runner owns
the requested execution timeout (at most five minutes). Abort, worker/service
disconnect and shutdown still cancel the pending action. Other actions retain
their two-minute deadline; authorization requests retain five seconds.

## OMP TUI timeline notices and compaction projection

`WorkerProjection` projects OMP timeline notices into canonical `NoticePart` items via `persistAndPublishNotice()`:
- `todo_reminder`: emitted when the model finishes with incomplete todos, detailing pending/in-progress items.
- `ttsr_triggered`: emitted when Time Traveling Stream Rules rewind a stream violation.
- `auto_retry_start` and `retry_fallback_applied`: emitted on model retry attempts and fallback transitions.
- `served_model_mismatch`: emitted when `upstreamModel` differs from served `model`.
- `cache_invalidation`: emitted when prompt cache reads drop to zero and cache write occurs.

Notices are persisted as native custom entries (`ohpichamber.notice.v1`) on the session branch and restored on cold history reload.

`session.compacted` projects authoritative compaction metadata (`method`: `soft-compacted`, `remote-compacted`, `shaken`, `snap-compacted`, `handed-off`), `tokensBefore`, `tokensAfter`, and markdown summaries. A manual `/compact` that OMP refuses as a no-op (`ManualCompactionNoOpError`: the branch already ends in a compaction or holds too little) surfaces as HTTP 422 `SESSION_TOO_SMALL` instead of an opaque 503; every other compaction error keeps its own surface, and the plan-approval compaction stays best-effort.
## Live tool catalog

`GET /api/agent/v1/sessions/:sessionId/tools` queries the live session worker's registered tools with their OMP tier (`read`, `write`, `exec`) and descriptions. When no live session is running, `GET /api/agent/v1/workspaces/:workspaceId/tools` queries the workspace worker, evaluating built-in tool availability against the native workspace settings via `resolveBuiltinToolPlan` so unavailable capabilities are marked `availability: false`. The Agent tool permissions editor consumes this endpoint to prevent selecting unavailable tools and triggering 422 `UNSUPPORTED_CAPABILITY` on profile activation.
## Native session archives

`SessionRegistry.archiveManifest()` is the host-authorized, read-only inventory of native chats. `exportArchive()` emits a bounded uncompressed ustar bundle containing the selected transcript, descendants, tool artifacts, subagent outputs, and referenced blobs; it never parses transcripts in Node. `importArchive()` validates the complete manifest before staging and installs immutable deleted-space references. Imported roots and descendants remain cold until explicitly reopened, and deleted-space mutations return `SESSION_READ_ONLY` (HTTP 409). Archive transfers are bounded to 256 MiB and five minutes per operation; save/restore uses a thirty-minute host window.
A cold deleted-space snapshot retains one journal per root or child session in memory so its cursor remains the same across repeated snapshots and can be validated by the following SSE request. Root archive deletion closes and releases those journals; service shutdown closes any remaining cold journals. The cache is process-local and does not make an archived runtime writable or reopen its worker.

## Session relocation and worktree archive concurrency fence

`SessionRegistry.prepareRelocation()` asserts worktree lease compatibility (`assertWorktreeLeaseAllows`) on both source and destination working directories *before* any session files are opened or moved on disk. It synchronously installs a relocation lease fence via `WorkerRegistry.acquireRelocationFence()`, synchronized through `withLeaseMutation`. While this fence is active:
1. Concurrent worktree archive lease acquisitions on source or destination directories are rejected with 409 `COMMAND_IN_FLIGHT`.
2. Attempts to relocate into or out of a currently leased worktree fail with 409 `COMMAND_IN_FLIGHT` before any file operations begin.
3. Finalization (`finalizeRelocation`) holds the same fence during subagent file moves, and rollback (`rollbackRelocation`) safely releases the fence under `withLeaseMutation` upon failure.

## Parent session linkage

`SessionBootstrap` and `HostSessionBootstrapSchema` accept an optional `parentSessionId: EntityIdSchema`. When provided, `SessionRegistry` initializes the runtime `SessionJournal` identity with `parentSessionId`, persists it to persistent session references via `references.put()`, preserves it on cold snapshot restore and live reopen, and includes it in `archiveManifest()` inventory and session listings.
## Fast session creation and deferred worker bootstrap

`POST /internal/sessions` supports `deferred: true` in `HostSessionBootstrapSchema`. When deferred, `SessionRegistry.createInitialSession` materializes the native session file on disk, stores its reference, initializes its in-memory projection with a stable initial epoch, and returns HTTP 201 with the `RuntimeSession` immediately, while `admit()` and worker launch execute asynchronously in the background. Subsequent prompt dispatches (`/internal/sessions/:id/runs`), mode changes, and branch controls queue behind worker readiness via `SessionRegistry.openingPromise(rootSessionId)`.

Catalog registration failures occurring after admission invoke `SessionRegistry.registrationFailed(rootSessionId, generation, cause)`, which transitions the session journal to `unavailable` with the causal message and settles any active run as `failed` with that reason. Stopping a worker on failed registration uses `WorkerRegistry.stopGeneration(rootSessionId, generation)` under `withRoot`, ensuring a replacement worker waiting in the root lock is never stopped.

If the service stops before deferred admission completes, the persisted session reference may not yet have an MCP configuration path. Reopen (including before delete) still validates the session's workspace and agent directory and can fill the missing path from admission. A path already recorded on the session cannot be replaced by a different path on reopen.

## Live session reopen

`POST /internal/sessions/:rootSessionId/reopen` is the Host's mutation restore call: a cold send/run, non-abort control, delete, fork and branch reopen through it, while reads stay on the cold projection and abort, steer, follow-up and rename do not reopen. The canonical session routes remember roots they confirmed live through a successful reopen or a validated run acknowledgement, so a warm send dispatches straight to `/internal/sessions/:sessionId/runs` with no extra reopen. Every failed dispatch, reopen failure, session delete, relocation and explicit worker unload forgets that confirmation; a later send verifies again. Only a well-formed refusal whose code is `SESSION_NOT_FOUND`, `SERVICE_UNAVAILABLE` or `SESSION_RESTORE_FAILED` — and not a `worker_capacity` refusal — reopens and re-dispatches that same command once, because such a refusal proves native admission never accepted it; `RUN_ACTIVE`, `COMMAND_IN_FLIGHT` and capacity refusals are never replayed. A reopen may promote a listed native session into the reference index before its first worker starts; promotion is bound to the listed workspace, agent-directory owner and root identity. For a root whose runtime is live, opened, not `unavailable`, and whose captured worker generation is still ready and connected, `SessionRegistry.liveReopenRuntime()` returns the existing runtime after the same captured-bootstrap and entry-scope comparison, without registering the workspace or agent directory, reconciling Host skill sources, re-registering the catalog worker, or creating a worker generation. Admission stays mandatory for cold (unloaded after service restart) or `unavailable` roots, which continue through `admit()` + `reopen()` and receive the actual new generation; a root already `opening` joins that pending open and its generation. A stopping or disconnected worker is not a live reopen, so the request falls back to admission, which refuses with 503 when the captured scope is gone.

Scope mismatches keep the existing refusals: the service compares the request with the captured worker bootstrap (403 `UNAUTHORIZED`, including `agentDirectoryId` when supplied), and `open()` compares it with the entry's captured input (409 `INVALID_REQUEST`; unloaded entries compare with the persisted reference). Native promotion additionally requires the listed workspace and agent-directory owner to match (403 `UNAUTHORIZED`), and refuses a native child addressed as a root (409 `INVALID_REQUEST`) before any reference write. `open()` also enforces `mcpConfigPath`, which the route's captured check does not. A reopen without `agentDirectoryId` keeps the admission path, which resolves the id it must compare. A missing reference is 503 `SESSION_RESTORE_FAILED`, a corrupt reference index or entry is 500 `SESSION_RESTORE_FAILED`, and a deleted-space root is 409 `SESSION_READ_ONLY`. A live reopen never publishes history from a previous runtime because it returns only the current runtime snapshot.

Native JSONL storage appends timestamped `custom` records when a runtime opens or disposes (`ohpichamber.private-roots.v1`, `session_exit`), so whole-file byte equality is not a stable transcript invariant. Session tests compare the parsed `message` records and the journal/history projection instead; a live reopen must preserve them exactly.

## Permanent session deletion

The Agent Service verifies the transcript against the live worker, stops the worker, and then removes the native transcript and artifacts before acknowledging deletion. Worker shutdown may write exit diagnostics, so removing storage before shutdown can recreate a deleted transcript.

## Named daemon ownership after promotion

The session worker's named-service ToolSession retains Host session identity overrides but binds session-change registration and launch-completion delivery to the actual native AgentSession. Inheriting those methods through `Object.create(nativeSession)` changes their receiver and cannot access OMP's private fields. Empty broker listings remain successful; actual listing failures still preserve existing shell service state.

Named daemon services remain owned by their broker session id after `/btw` promotion. `WorkerRegistry` retains the retired ids across worker retirement for the lifetime of the supervisor and passes that lineage through private worker bootstrap. `WorkerShell` authorizes listing, logs, stdin and stop against the current id and those retired ids only, while projecting every service under the current session and worker generation. Catalog aliases are generation-scoped and are not the service ownership authority. Supervisor restart does not restore this in-memory lineage.

## Worker capacity and idle eviction

`WorkerRegistry` counts only `kind: 'session'` roots against the measured Task17 cap (`WORKER_CAPACITY_POLICY`: 5 active root workers, 600000 ms idle timeout, 30000 ms reap interval). Stateless catalog and usage workers are workspace overhead and never consume a root slot. A new or replaced root reserves its slot synchronously before the asynchronous bootstrap, so concurrent opens cannot oversubscribe; a root beyond the cap receives HTTP 503 `SERVICE_UNAVAILABLE` with `details.reason: "worker_capacity"` and the current/maximum counts, while existing workers stay untouched. An existing root at the cap may still reopen, restart or receive work.

The reaper considers a session worker idle when its last worker message or dispatched operation is older than the timeout. Eviction also requires no active run or pending prompt (`SessionRegistry.isIdleForEviction()`), no pending worker operation or Host action, no unresolved approval or question, no lifecycle mutation or opening, no restart reservation (`WorkerRegistry`), and no running background Shell job (confirmed by the worker's own snapshot). Eviction reuses the graceful `stopEntry` path; the root becomes `unavailable` and reopens cold from its persisted native transcript. Active turns, background Shell jobs, and pending approvals are never evicted. The reaper timer is unreferenced, so it cannot keep the service process alive.

`DELETE /internal/workers/:rootSessionId` explicitly unloads an idle root worker on demand through this same eviction path: it verifies that no active run, pending worker command, restart reservation, or background shell job is active (returning 409 `RUN_ACTIVE` or `COMMAND_IN_FLIGHT` otherwise), evicts the worker gracefully, transitions the runtime to `unavailable`, and allows the session to reopen cold with native history intact upon subsequent interaction.

## Explicit plugin application

`POST /api/agent/v1/workspaces/:workspaceId/plugins/apply` with `strategy: "restart-idle-sessions"` applies the persisted plugin revision without incrementing it. The owner-wide operation captures current session generations, then `SessionRegistry.restartIdleSessions()` reserves every selected root before any retirement. Active runs, pending prompts, controls, interactions, child-index writes, worker commands, Host actions, lifecycle mutations and running background Shell jobs refuse the whole preflight without stopping any selected worker. Reservations block competing commands until the operation settles.

Accepted roots restart through the existing catalog admission and native session-open path using their persisted transcript files, options, scopes and child references. Each successful outcome identifies the actual new worker generation; a failed stop, startup or registration is reported as failure without retries or fabricated runtime success. Persisted configuration and transcript references remain available after a failed restart. Web/PWA, Electron, hosted mobile and Capacitor all reach this through the same authenticated Host Gateway; Node and UI processes never load native plugins. Plugin mutations do not restart active sessions automatically.

Application holds the coordinator's admission/mutation exclusion across target capture, preflight, all restarts and result publication. Each restart reuses the captured non-reentrant admission authority rather than reacquiring the same serial lock; existing worker scope validation and catalog registration still apply. Explicit Apply restarts only sessions sharing the requesting native plugin root, not other named profiles affected by shared workspace files. Successful outcomes use the actual loaded worker's captured plugin revision and must agree with that owner revision.

## Stateless workspace worker refresh

A registered workspace pre-warms its stateless worker in the background, so the first models or providers read does not pay worker startup; a failed pre-warm surfaces on the next real read instead of failing registration. Read-only catalog operations (`catalog.models.read`, `catalog.providers.read`) execute concurrently and advance no owner revision, while every mutation keeps the agent-directory serialization and CAS winner.

A ready stateless worker is reused only when its execution scope, working and agent directories, configuration paths and complete effective spawn environment still match. Revision cursors alone are not execution identity and do not recreate it. A changed profile or environment requires a clean idle stop and a newly initialized worker before native ownership is authoritative again; it is never a relabel of a cached process. Pending commands, completions, Host actions and lifecycle controls refuse replacement instead of cancelling active work. The effective environment is an explicit process/locale/proxy/OMP allowlist plus the Host-authorized directory overlay; the overlay cannot supply `OHPICHAMBER_INTERNAL_SECRET`, `OPENCHAMBER_MANAGED_PROCESS_TOKEN` or `PI_CODING_AGENT_DIR` (case-insensitive), which the registry deletes or sets itself before launch; `OMP_PROFILE`/`PI_PROFILE` remain authorized overlay values for named profiles. That environment is captured once for comparison and creation. Provider credentials are not inherited from the Host process: supported sources are the authorized overlay and OMP `AuthStorage`.

## Native plugin catalogs

Canonical workspace `/plugins` routes dispatch private typed envelopes to Bun workers. `NativePlugins` constructs fresh native `PluginManager` and `MarketplaceManager` instances per operation so SDK file caches cannot hide another workspace's committed changes. Node performs authentication, authorization, schema validation and routing only; neither Node nor UI imports native plugin code.

Native package install/update/remove operations belong to the actual native profile/XDG plugin root, not to an inferred parent of an agent directory. A private worker identity RPC resolves that normalized root, the nearest native project registry and the exact authored-source directory; paths remain private. Root-keyed plugin revision CAS is persisted independently of provider/agent revisions. Global mutations and explicit Apply select roots sharing the actual native plugin owner even when agent-directory labels differ. Marketplace project mutations select roots sharing the native nearest registry; local source mutations select roots sharing the exact source directory, including other profiles. Persisted bindings advance every affected known native owner counter independently. Other profiles remain explicitly stale until Apply is requested in that profile; successful Apply only restarts same-owner roots. Catalog runtime inventory remains scoped to the requested workspace and marks old-profile roots unavailable instead of relabeling their previous applied revision.

Native plugin reads, writes and explicit application share the catalog coordinator's admission exclusion. Captured plugin revisions remain stable across native session construction and runtime publication. Root-owner serialization wraps mutations and Apply; the entire idle-root restart operation holds coordinator exclusion and passes captured non-reentrant admission authority through the existing validated admission path, never reacquiring the same coordinator queue. Named native profiles are preserved during runtime initialization instead of being erased by an unrelated agent-directory override. Doctor output redacts native config/XDG/plugin locations, and public mutation errors never include native install or registry paths.

`GET /plugins` reads installed metadata and cached marketplace catalogs without network access. `GET /plugins/marketplace` is an explicit refresh: it invokes native `updateAllMarketplaces()` before reading catalogs, and is enterprise-gated with package-manager install/update/remove operations. Enablement, settings, diagnostics, cached catalog reads and local authoring remain on this machine. A failed authoritative read is an error, not an empty replacement catalog.

Plugin settings are native JSON values validated against each declared native setting definition before any writes. Settings writes explicitly select `settingsScope: "global"` independently of package/marketplace install scope and always use native `setPluginSetting`/`deletePluginSetting`. A submitted object replaces explicit declared nonsecret global values, deleting omitted nonsecret keys while preserving omitted secrets. The catalog distinguishes saved `globalSettings` from effective `settings`: existing project overrides remain read-only native inputs, with per-key `globalConfigured` and `overridden` flags. Public values include only declared nonsecret keys; declared secrets expose presence flags, never values, defaults or environment contents. No settings operation creates project overrides or shadows an inherited project registry. Native configuration snapshots restore prior files after a partially failed configure operation.

## Native extension control center

Canonical workspace `/extensions` routes reuse the catalog coordinator and its owner-revision CAS; they are not a second unconnected API. `GET` returns an `ExtensionInventoryState` for the agent-directory owner, `PATCH` accepts an `ExtensionToggleRequest` carrying `expectedRevision` and returns the post-write state. A stale `expectedRevision` is rejected with 409 before any native write. Reads never mutate a revision.

`NativeExtensions` projects every registered discovery provider from `getAllProvidersInfo()`, including providers that discovered nothing, so the control center can show a master switch for each. Rows come from typed native capabilities loaded with `includeDisabled: true`, so disabled, shadowed and gated rows stay visible instead of silently disappearing. Shadowed rows are identified by the winning row's real provider and display path, never by same-name guessing.

Provider switches persist native `disabledProviders`; per-item switches persist native `disabledExtensions` using each capability's own real `toExtensionId` identity. `userSource` switches persist only `enabledProviders`, so opting out of a foreign user-level tree leaves project configuration untouched. Kinds without a native per-item identity (SSH hosts) report `toggleable: false` and refuse a toggle with 422 rather than inventing an identity. Writes follow the native settings discipline: reload, validate, set, flush, reload, and report a `SERVICE_UNAVAILABLE` failure instead of claiming success.

Native settings and the native plugin root are different owners with different revisions. The UI keeps an independent extension revision, reads the authoritative `/extensions` revision immediately before a write, and never overwrites the plugin catalog revision with an extension revision or vice versa. The inventory embedded in `PluginCatalogState` is initial display only; an explicit `/extensions` read replaces it for the same workspace.

The projection is display-safe: host roots become `<agent>`, `<workspace>`, `~` or an abbreviated tail; MCP rows publish only transport and URL hostname, SSH rows only host, username, port and description; warnings containing absolute host paths are dropped. Knowledge bodies (skill, rule, prompt, slash-command, context-file, instruction) are published as inspector content, while credentials, headers, environment values and private key material never are. Web/PWA, Electron, hosted mobile and Capacitor reach this through the same authenticated Host Gateway; Node and UI never load native discovery.

## Local native extension source

Local source authoring owns only flat `.ts`, `.js`, `.mts` and `.mjs` filenames beneath the selected workspace's `.omp/extensions/`. Parent directories and source files reject symlinks; source reads use no-follow descriptors. Bun parses source without evaluating uncommitted code before an atomic temporary-file replacement. A syntax failure leaves the previous file intact. Import/factory evaluation remains a real native session-load operation: evaluation errors prevent readiness or produce an explicit failed restart outcome, never an invented apply success.

New sessions resolve enabled native plugin paths and authored extension paths into the SDK's explicit extension-root lane, retaining Host observer and approval factories. The SDK cannot replace newly imported extension modules in an existing session through transcript reload. Ordinary configuration/source mutations therefore remain committed even when active roots report `RELOAD_REQUIRED`, preserving their last confirmed applied revision. Only the explicit idle-session restart operation changes those active runtimes.
## Native file resources

`WorkspaceRoutes` exposes workspace command and prompt-template CRUD and expansion through namespaced `fileResources` worker envelopes. `NativeFileResources` loads slash commands with `loadSlashCommands`, templates with `loadPromptTemplates`, and skills with `loadSkills`; expansions use the native slash/template functions and skill prompt builder. Listing and expansion never create a conversation or invoke a model.

`POST .../commands/expand-text` prepares raw input through the native command-then-template pipeline once and returns an authoritative `command`, `template`, or `text` match kind. Bindings belong to the top-level invocation, not a slash-looking generated body. No-match text is unchanged. UI and scheduled senders use this same worker owner before capturing a canonical prompt; session dispatch deliberately keeps automatic SDK expansion disabled, preventing a second expansion of prepared text.

Commands and templates share the existing selected-agent catalog revision/CAS owner. Creates and updates publish complete Markdown files using a same-directory temporary file; new names cannot overwrite a concurrently created file. Renames preserve the old file if destination publication fails. Application model/agent/group metadata is stored in `openchamber` frontmatter; existing unrelated frontmatter survives updates. The public content field is the native Markdown body, not a second frontmatter format.

Writable files are confined to the admitted workspace `.omp/commands` and `.omp/prompts`, or the selected agent directory's `commands` and `prompts`. Every managed path component is checked for symlinks and realpath containment, and checked again before publication. This follows the portable Host filesystem convention; it does not claim protection against hostile same-user directory replacement between filesystem calls. Native inherited/external layers remain read-only and expose opaque IDs, not private paths.

Skill file commits and their source revisions remain Host-owned. Workspace native skill discovery exposes a separate opaque expansion ID and optional `authoredSkillId` only for a confined managed `SKILL.md`, so clients never infer write authority from names. `POST /internal/workspaces/:workspaceId/skill-files/commit` captures an authorized opaque operation ID and holds the existing coordinator lifecycle queue through Host source reconciliation, the trusted Host file-commit callback, durable source publication, and captured-generation fanout. Model tool actions cannot invoke this dedicated `host.skill-source` IPC channel. Its completion waits for the real Host reply or channel shutdown, not a timeout that could release admission while a disk commit is still running.

Root admission reconciles Host source journals under that same queue before native discovery, so a service-only restart cannot load committed files under an older source pair. `POST /internal/workspaces/:workspaceId/skill-files/reconcile` provides the same explicit recovery for Host file reads without replaying runtime apply. `POST .../skill-files/apply` uses the same coordinator fanout and generation finalization as session-scoped apply, including explicit partial/failure and no-active-worker results. Persisted source revisions never imply active application.

Raw `SKILL.md` content remains exact Markdown. Skill descriptions and expanded prompts reuse the established session skill privacy helpers: the native builder receives the public `skill://` base URI and private roots are redacted from public expansion messages. This is the existing catalog privacy contract, not a new authoring-content transform.

Web and Electron reach these operations through the authenticated Host Gateway. Hosted mobile and Capacitor use that same configured Host; no client or Node Host imports the SDK.
## Host tools and native internal URLs

The worker registers `openchamber`, `web`, `memory` and `notify` as essential extension tools, so OMP presents them in the ordinary callable tool schema with only their own descriptions. Their `execute` path still calls the Host action owner; they are never `xd://` devices in the chat prompt.

Native `read` targets may be OMP internal URLs. The supervisor's execution-free descriptor normalizes a target with OMP's `InternalUrlRouter` and admits only `agent`, `history`, `artifact`, `local`, `proc`, `skill`, `xd`, `mcp`, `omp`, `issue` and `pr` into the Host authorization request. Host policy accepts those internal targets only for `read`, still checks every local path in a mixed delimited list, and leaves `edit`, `grep` and `glob` on the filesystem-only path.

A native `write` may target OMP's `local://` session artifact sandbox, which is where Plan mode drafts `local://<slug>.md` before proposing it. The descriptor carries those targets as `internalWriteUrls` (schema-restricted to the `local` scheme) instead of `destinationPaths`, and the Host admits them only for the `write` tool and only when the workspace grants `fileTools: ['write']`. Every other internal scheme stays read-only for a write, a real filesystem destination is still contained to the workspace, and `write` with neither a destination nor an internal write URL remains refused. Unknown schemes and NUL bytes remain refused. Native `wait` observes only this session's async jobs and is admitted without a machine capability.

## Native web search

`GET`/`PUT /api/agent/v1/workspaces/:workspaceId/web-search` and credential `PUT`/`DELETE .../web-search/credentials/:providerId` use the strict canonical web-search schemas. Credential path and body identities must match. The workspace must be registered by the authenticated Host; no session is required to read or persist settings. These HTTP operations serve web/PWA, Electron, hosted mobile, and Capacitor through the existing canonical Host transport.

`WebSearchCoordinator` serializes reads, mutations, and root admission by the registered native `agentDirectoryId`, not by workspace. The stateless worker owns native settings persistence and revision CAS; the supervisor never imports SDK objects or exposes credentials in public responses. A successful durable mutation fans out `apply` to every active root sharing that native settings owner across all workspaces, using the captured worker generation. Unrelated native owners remain unchanged. Admission uses the same barrier, so a concurrent opening either joins the mutation's fanout or starts after its durable commit.

Persistence failure returns `failed` without applying uncommitted settings. Persisted mutations with any worker failure return `partial` even when every application failed; persisted mutations without failures (including zero live roots) return `applied`. Worker errors expose codes, never native exception text or secrets. A revision conflict returns HTTP 409 `CATALOG_CONFLICT` with `details.currentRevision` and the current authorized redacted `details.state`; failed reads never masquerade as empty settings.

The worker exposes `providers` from the native registry's available search-kind model pool, so every catalog entry is a native `web/*` search engine. Chat models that declare a grounding transport remain valid native web-role and fallback selectors and keep resolving during search execution, but they are not catalog entries. A persisted chat selection that resolves against the available native web-role pool is kept by GET, survives non-selection settings updates, and appears in the UI as a missing catalog provider. The pre-existing role-chain projection still omits configured selectors whose provider is unavailable, so a client that resubmits such a projected chain can drop them. Newly submitted selectors outside the available native web-role pool are rejected. Settings use the process singleton backed by the owner's `agentDirectory/config.yml`; credential writes and removals use `AuthStorage.credentials.set/remove` with the native transport's exact namespaces. Revision CAS uses a durable mode-0600 sidecar under the native OS file lock. It reserves a uint64 revision token before mutating native state, so a failed native write still consumes that token. A failed pending SDK save quarantines the worker against later writes, replay, and search egress.

Every cached native search transport checks the enabled setting and then requests Host authorization with `{ type: 'web-search' }` immediately before searching. This includes explicit provider selectors and the XAI transport chain; cached transport objects do not bypass the live authorization boundary.

The session tool observer routes the exact native SDK `web_search` tool name to that same `{ type: 'web-search' }` authorization after the selected profile's `allowedTools` check. Other tool names keep the generic descriptor/approval-aware path. Host enterprise policy therefore refuses search before the provider transport, with no request egress.

## Historical usage

`GET /api/agent/v1/usage` reports OMP's own statistics for every OMP session in the default agent directory, TUI sessions included. Before each report the usage worker runs OMP's incremental sync (`syncAllSessions`) and reads `stats.db` only. A failed sync or database read is an error. It is never an empty report. Queries carry optional inclusive `from` and exclusive `to` epoch-millisecond bounds (omitted `to` defaults to now), an explicit viewer IANA timezone, an optional provider, and optional canonical workspace/project filters. A workspace or project filter resolves to the sessions folders of the Host-authorized roots in that scope, and every aggregate (sessions, prompts, steps, tokens, cost, activity, providers, models) is limited to transcripts under those folders. Sessions that no registered root references, in a folder no root has, appear only in the unscoped view.

Pricing comes from OMP's configured model registry for the default agent directory (bundled catalog plus `models.yml`), so a configured custom model prices from its own rates. Unknown pricing is `null`. Reasoning tokens come from each request's transcript entry, for assistant turns and `model_usage` auxiliary calls alike, counted once per request. `output` already includes reasoning, so `reasoning` is never added to `total`. Provider TTFT and tokens per second are request-weighted from summed samples. Prompts are attributed to a provider through the assistant that answered them.

`accounts` carries OMP's native AuthStorage usage reports and recorded usage history for the window, projected to quota and usage fields. The usage worker opens the default agent's AuthStorage per request, and it never returns credentials, account identity, or raw provider payloads. Each source fails on its own: a failed reports or history read is `null` and named in `errors`, and the stats still return.

`/usage/tools` remains a Host-authenticated read over the registered references. "All" there means their intersection with the Host's authorized scope set. No client path participates.

A cold usage worker runs these reads and constructs no provider and no live session. Native SDK imports stay worker-private. Unfinished tool calls remain unfinished, and historical activity never establishes current runtime status.

Failures are per source, with sanitized error codes. Valid siblings survive with `partial` status. Failure of every tool source is an error, not an authoritative empty report.

## Native workspace cache warming

`GET` and `PUT /api/agent/v1/workspaces/:workspaceId/cache-warming` use the existing authorized workspace catalog owner and uint64 revision CAS. The canonical contract is `agent-contract/src/warming.ts`. PUT returns `persisted` configuration separately from generation-qualified active-root outcomes (`applied`, `partial`, `failed`, or `no-active-workers`). Stateless configuration workers are not active-session execution proof; stopped roots are not started for fanout.

Only Bun SDK workers read native Settings, persist `cfgProvidersCacheWarming`, flush, and call `AgentSession.setCacheWarmingMode`. Native typed setting writes are global, so the stateless writer scopes its isolated writable Settings to the workspace `.omp/config.yml`; authoritative reads use the real agent directory to preserve inherited native settings. Session startup reapplies the latest effective workspace mode before readiness. Live application uses a session-only override and does not rewrite configuration. Native `CacheWarmer` owns scheduling and provider traffic; no Host/UI keep-alive loop is added.

Web/PWA, Electron, hosted mobile and Capacitor use the same authenticated selected Host route. Mobile remains UI-only. Warming stays with the session's provider and creates no provider-entry or network-exposure capability. Configured mode is not proof that a request ran or a cache hit occurred.

Native Settings flush precedes the existing service catalog-revision file commit. If persisting the service revision file fails after native Settings have flushed, the native configuration remains saved on disk while the supervisor restores the previous service revision in memory, skips live application (`liveApplication: 'not-started'`), and returns HTTP 503 `SERVICE_UNAVAILABLE` with typed `CacheWarmingPartialWriteDetails` (`{ workspaceId, configuredMode, currentRevision, nativeConfigurationCommitted: true, liveApplication: 'not-started' }`). The system does not claim atomic rollback across the native file write and service revision file. The UI checkbox catches this 503, displays the saved mode alongside a partial-write error message, and disables further writes until reload. An authoritative GET reports the effective native mode with the service's last committed revision. This follows the existing catalog durability boundary rather than introducing a second transaction protocol.

## Native approval projection

The worker captures the exact native tool input for Host authorization and keeps it service-private. The public approval record carries the actual tool name and a redacted, truncated one-line input summary (the bash command or file path); the card never renders a raw input object. `always-allow` resolves OMP's native `allow_always` handle in the worker's per-session ACP decision cache (bash cache key): OMP suppresses later bash cards for that key, while each cached call still reaches the custom Bash tool and receives its own exact execution grant before authorization. The cache resets with the native logical session, stops with the worker, and is never persisted to the Host policy store or OMP config. Provider-safety and Host-only prompts never receive it. The native approval handle is resolved with OMP's Approve or allow_always choice. Schema version 2 revokes legacy session allowances.

## Permission modes for tool execution approvals

Tool execution approvals are the requests that may be approved for the user: the native ACP permission gate (`WorkerInteraction.requestPermission`) and the native approval extension's tool requests, which share `InteractionManager`'s single `requestApproval` path (`approveBash`, `ui.approve`, and an observed `ui.select`). Those records carry `permissionRequest: true`, and the worker sets it on the shared `requestApproval` path so every native tool whose approval wrapper uses `ui.approve` or an observed `ui.select` is covered too, not only the ACP gate. Unobserved `ui.select`, `confirm`, `input`, `askDialog`, plan review, native-grant re-authorization and provider/Host authorization never pass through that method and always stay on screen.

Each session resolves a mode from the Host: `ask` shows the card, `auto` answers it, `safety` asks the Host safety net first. The mode is never cached in the service; it is read over private IPC (`permission.mode.load`) when a request arrives, so the Host stays the single authority. A workspace or session deny policy always wins and is rejected at request time and again immediately before any programmatic approval.

An approval the policy answers itself publishes no canonical events: there was never a card to show or to resolve. A card that stays is published once as `approval.requested`, and a resolution publishes `approval.resolved`. For `safety`, the accept is only consumed after a second read confirms the record is still pending, the epoch and worker generation still match, the mode did not change while the classifier ran, and no deny appeared.

The Host pushes a mode change to `POST /internal/sessions/:id/permission-mode`, and `SessionRegistry.reconsiderPermissions` re-evaluates every pending execution approval of that session, so a switch to `auto` answers a card that was already waiting.

## Goal verification and the turn cap

Each session worker owns a `GoalVerifyingController`, a subclass of OMP's native `RpcGoalController`. OMP keeps ownership of continuation, the tool set and the completion journal; the subclass only decides whether the next continuation is allowed:

- A terminal `agent_end` with an active goal starts the check, and `continuationPending` is true while it runs, so the session is never reported settled mid-verification.
- After the verdict the same terminal event is handed to the native controller. A `complete` verdict calls `completeGoalFromTool()` first, so OMP journals the completion from that event and no later event is needed; a `paused` verdict pauses the goal.
- The judge is OMP's `resolveJudge` with purpose `goal-verification`, the session cost gate and `journalJudgmentUsage`, so billed attempts land on the session ledger. With `sessionGoalChecker: 'classifier'` (default) the `judge` role is used; `'small-model'` words the `smol`, `tiny` or `default` selector into the `judge` role.
- The check sees the objective, the last eight message texts and tool calls, the todo phases and tokens used. A failed or unresolvable judge produces no verdict: native continuation stands, and the cap still applies.
- The cap (`sessionGoalMaxAutoTurns`, 1–200) counts turns per goal id; reaching it pauses the goal. A new goal, and an explicit `create`/`resume` of a paused one, re-arm the counter and the abort signal, so resuming diverts to a fresh budget instead of instantly re-hitting the cap. The check itself reports settled as soon as it has decided, so a just-paused goal is resumable without waiting for the promise to unwind.
- `stopForHostAbort` aborts the in-flight judge, and a verdict for a replaced, dropped or paused goal is discarded.
- When the verdict ends the goal, the controller reports a dropped continuation so the Host's pending-continuation marker clears.

The Host captures both preferences into the worker bootstrap environment (`OPENCHAMBER_SESSION_GOAL_CHECKER`, `OPENCHAMBER_SESSION_GOAL_MAX_AUTO_TURNS`); they are non-secret and take effect for workers admitted after the change.

## Plan mode and subagent delegation

Plan mode keeps its own tool set. When `OPENCHAMBER_PLAN_ALLOW_AGENTS` is set in the worker bootstrap environment (Settings → Sessions → "Allow subagents in Plan mode"), `enterPlan` and the plan restore keep the native `task` tool active alongside the plan tool set. Leaving Plan mode restores the previous tools, so the permission never outlives the mode. It grants no capability of its own: every child tool call still passes its own authorization.

## Native goal mode

The three-run native goal fixture disables `suggestion.generator`: background
composer predictions reuse the provider and its tool catalog but are not goal
runs. Its scripted response counter must count only foreground goal requests;
suggestion generation has its own driver tests.

Session control accepts `goal` operations `create`, `pause`, `resume`, and `drop`. Creation requires a nonempty objective and accepts a positive integer token budget (or `null` for no budget). The Host authorizes the session scope and forwards the operation; it stores no native goal state. Create and resume refuse an active run; pause and drop remain available during execution.

Each session worker owns an unchanged OMP `RpcGoalController`, enables the session-local `rpc` continuation mode, and feeds it every native event. Continuation submissions become canonical `origin: 'goal'` runs through the same worker-run projection used by plan approval. Abort stops the controller before aborting the native session. Reopened active goals restore paused rather than silently starting work.

`SessionMode` publishes the objective, native status, optional budget and tokens used. A dropped goal reports Main. Completed goals retain a terminal display record even though OMP exits its active goal mode. Native controls do not write legacy Host supervisor metadata; that supervisor remains for entry points not yet migrated.


## Speculative session preparation

`POST /api/agent/v1/sessions/prepare` speculatively admits and boots a session worker for an authorized workspace before prompt dispatch. Preparation is bounded to at most one session per workspace, returns `{ ok: true, sessionId }`, and carries no user content or secrets. `POST /api/agent/v1/sessions` adopts an in-flight or completed prepared session without duplicating admissions or creating conflicting root scopes. Unused prepared sessions are reaped after 5 minutes via an unreferenced timer, and `DELETE /api/agent/v1/sessions/prepare` discards the prepared session when the client draft is closed.


## Session listing and titles

`GET /api/agent/v1/sessions?workspaceId=...` merges the Host-authorized workspace's persisted references with OMP's own directory listing (`SessionManager.getDefaultSessionDir` plus `listSessionsReadOnly`/`isEmptySession` in `session-listing.ts`). Sessions created outside the app appear by their OMP identity and title; a referenced session keeps the Host's opaque `rootSessionId` and is correlated to OMP storage by its session file. Listing reads JSONL headers only and starts no worker. `RuntimeSession.title` carries OMP's title and timestamps come from OMP's file metadata.

`PATCH /api/agent/v1/sessions/:sessionId/title` accepts `SessionTitleRequest` (`workspaceId`, `title`). A live root applies OMP `SessionManager.setSessionName(title, 'user')` through the worker; A worker titles an unnamed root once its first turn settles: it asks the selected (and Host-authorized) model for the opening prompt under OMP's own title policy, and on a null answer retries once from the finished exchange itself through OMP's `<chat><user>…</user><assistant>…</assistant></chat>` context — the same `#advanceDeferredTitle` shape, in the same `agent_end`, without a second prompt. That retry is the only place the default title policy is replaced: OMP's prompt answers `<title/>` for greetings, which would leave a greeting-only session `Untitled` forever, so the deferred attempt passes a conversation-subject prompt through `session.generateTitle(context, customSystemPrompt, signal)`. It keeps OMP's `<title>` output contract, 3–6 words and the user's own words, asks for the subject of the exchange that already happened, forbids an empty title and forbids inventing a task the user never named. The selected model stays pinned, fallback stays disabled, and provider authorization is unchanged. The attempt is aborted by the next prompt and by worker close, and a manual rename or an existing title always wins. a cold referenced or unreferenced session opens OMP's session manager for that JSONL, writes the title, flushes and closes. The live projection also subscribes to OMP's session-name change and publishes `session.updated { title }`, so an auto-generated title reaches open clients without a refetch. Host metadata no longer stores titles. Usage records publish an optional `reasoning` counter beside `input`/`output`/`cacheRead`/`cacheWrite`; it is provider-reported and informative, so `totalTokens` keeps the provider's own full count and no consumer adds reasoning on top of it.
